A Simulation-to-Reality Study
Project report, revision 3
Stage 1 results and Stage 2 plan
Guide: Dr. Radhika Joshi
Department of Electronics and Telecommunication Engineering
COEP Technological University, Pune
2 October 2026
Abstract
Mobile networks react to congestion after users already feel it. This project asks two questions. First, can the standard measurements that an O-RAN base station already reports every 250 ms warn that a user will be starved of radio resources about one second before it happens? Second, and more important, does a predictor trained on simulated data still work on real network data?
The work is split into two stages. Stage 1, completed and reported here, builds the data. It repairs an OMNeT++/Simu5G city-network simulation and runs six scenarios (22 runs, 485,546 user-intervals); reduces the public TRACTOR O-RAN dataset to its slicing-free part (601,592 user-intervals, 188 users, 33 conditions); maps both onto one set of six measurements in identical units; labels congestion with the same code on both; and produces train and test sets for five experiments. Stage 2 trains and compares the prediction models on those sets.
Stage 1 also produced results that change the method. The two-peak shape on which the earlier label was built is an artefact of network slicing, not of congestion. In the real data, starvation rises with load, from 0 % of active intervals with one or two users to 48 % with eight. The repaired simulator now congests, from 0.9 ± 1.7 % (light load) to 29.2 ± 4.3 % (urban) and 52.5 ± 1.1 % (heavy load) of intervals. Before any model is trained, the two sources already differ: starvation is fifteen times more common in simulation (34.1 % against 2.2 %), and four of the six shared measurements are far apart in distribution. These numbers set the bar that Stage 2 must clear.
Keywords: O-RAN, near-real-time RIC, congestion prediction, simulation-to-reality transfer, E2SM-KPM, Simu5G, TRACTOR.

1. Introduction
1.1 The problem
Radio access networks today react. A scheduler notices that a queue has filled, or that delay has crossed a threshold, and responds; by then the user has already seen the video stall. Yet the base station measures a great deal several times per second: how much data waits for each phone, how many radio resources each phone asked for and received, and how good each phone's radio link is. These numbers change before the stall. This project asks whether a model fed only those numbers can say this user will be starved about one second from now early enough for the network to act.
1.2 What changed: O-RAN
Historically a base station was a sealed box from one vendor; fine-grained measurements could not be read out and third-party software could not run inside it. O-RAN splits the base station into parts with standard interfaces and adds the near-real-time RAN Intelligent Controller (near-RT RIC), which hosts applications (xApps) on control loops between 10 ms and 1 s. Per-user measurements now flow out over the E2 interface, and an xApp can act on them within the same loop. A one-second warning finally has somewhere to go (Section 3).
1.3 The gap this work addresses
Predicting congestion inside a simulator is not hard, and it has been done many times, including in our own earlier work. Almost all published work trains and tests on data from the same source, which measures interpolation rather than generalisation. A model trained on a simulator may learn the simulator's quirks rather than anything true about networks. This project deliberately trains on simulated data, tests on real O-RAN telemetry, and reports the size of the gap, including if it is unfavourable.

Figure 1 shows the whole project on one page. Stage 1 builds the data from both sources and ends with ready-to-use datasets; it is complete. Stage 2 trains baselines and models on those datasets and runs the five experiments; it is the next step. Stage 1 contributes:

2. Scope, aim and objectives
2.1 Scope
The scope is defined by the measurements the model may use: only quantities that a base station reports over the standard E2 key-performance-measurement service model (E2SM-KPM) and that exist in both the simulated and the real data. Section 4 lists the six that qualify and explains why the others are excluded. All measurements are aggregated into 250 ms intervals, the reporting period of the real dataset. The target is the onset of starvation for one user, one second (four intervals) ahead. Onset rather than state, because starvation persists: a user starved now is still starved one second later 72 % of the time (Section 7.2), so predicting the state forward is nearly trivial and says nothing about when trouble begins.
Out of scope: packet inspection or user payload, closed-loop control (the model raises an alarm and does not act), millimetre wave, and multi-vendor interoperability.
2.2 Aim
To develop and evaluate a congestion-onset predictor whose inputs are restricted to measurements obtainable over the E2 interface, to quantify how much of its performance survives the move from simulated to real O-RAN telemetry, and to establish whether it fits within near-real-time RIC timing.

3. Where the model sits: O-RAN in brief
Figure 2 shows the target deployment. The base station is split into three logical nodes. The O-DU (distributed unit) runs the MAC scheduler, which every millisecond decides which phone gets which physical resource blocks (PRBs); most measurements used here originate there. The O-CU-UP (central unit, user plane) carries user data through PDCP and so knows delivered throughput. The O-CU-CP (central unit, control plane) handles connection set-up and mobility and knows each phone's serving cell. The O-RU radio unit transmits over the air.
Above them sit two controllers. The near-RT RIC reads measurements over E2 and hosts xApps that decide within 10 ms – 1 s; the congestion predictor is designed as such an xApp. The Non-RT RIC / SMO trains and manages models on a slower loop and sends policies over A1; A1 carries no telemetry. Restricting inputs to E2-reported quantities is what makes the model deployable without access to node internals or to the phone. End-to-end latency is not reported over E2, which is why it is not an input. Deployment itself is outside this project.
Figure 2. Target deployment. The predictor runs as an xApp on the near-RT RIC (coral) and reads measurements from the RAN nodes (teal) over E2 every 250 ms. Each node box names the measurements it produces. This placement is a design target; deployment is not performed here.
4. Key performance measurements: what each one achieves
Revision 2 listed the measurements by their names. This section orders them by the question each one answers about the network, states what each achieves for the prediction, and traces each to the part of the system that produces it.
4.1 How the measurements connect to congestion
Congestion in a cell is a shortage of PRBs. Every 250 ms a user needs a number of PRBs, set by how much data is waiting and by how many bits each PRB can carry for that user's radio link. The user gets a number of PRBs, set by how many are still free in the cell and by the scheduler's fairness rule. When a user gets less than half of what it needs, it is starved: its data queues, its speed drops and, a little later, the user notices. Figure 3 shows where each measurement enters this chain.
Figure 3. How the shared measurements relate to starvation. Radio quality sets how many PRBs a user needs; cell load and link errors limit how many it gets; starvation then shows up as lower speed. The scheduler sees the shortfall before the user does, which is the window prediction exploits.

6. Methodology
Figure 1 (Section 1.4) shows the method. Sections 6.1–6.5 describe Stage 1, which is complete; Sections 6.6 and 6.7 describe Stage 2, which is planned.
6.1 Stage 1: repairing the simulator
The simulator is OMNeT++ 6.4.0 [23] with INET 4.6.0 [24] and Simu5G 1.4.3 [1]. A review of the configuration against the Simu5G source code, followed by real runs, found the faults in Table 8. Several were silent: OMNeT++ ignores a configuration line that matches nothing, and the first matching line wins, so a setting could look correct and have no effect.
Table 8. Faults found in the simulation and the parser, their effect, and the fix.
On Windows two further problems appeared: INET 4.6.0 did not export two classes that Simu5G needs (fixed by back-porting the upstream INET correction), and the per-vector buffer reservation exhausted memory when three runs started together (fixed by declaring vectors only once they hold data). Neither affects results.
6.2 Stage 1: the simulated scenarios
The network covers 1 km × 1 km: one macro cell (46 dBm) in the centre, three micro cells (30 dBm), and four interference-only cells at the corners. Fifty phones move by random waypoint at 1–5 m/s. The carrier has 50 PRBs at 15 kHz spacing (10 MHz, 1 ms slots) and a proportional-fair scheduler. A server sends constant-rate downlink traffic to three groups: video (users 0–19, 2.8 Mbit/s), web (20–34, 0.2 Mbit/s) and IoT (35–49, 32 kbit/s). Every phone also sends 40 kbit/s uplink, and users 0–29 add an 0.8 Mbit/s uplink burst between 50 and 65 s. Each run lasts 120 s.
Table 9. The six scenarios.
6.3 Stage 1: preparing the real data (TRACTOR)
TRACTOR [2], [25] replays real smartphone traffic (video streaming, browsing, file transfer, video calls and background activity) through a complete srsRAN-based O-RAN system on the Colosseum radio emulator; an xApp records each phone's measurements every 250 ms over E2. It is a real protocol stack, a real scheduler and real traffic over an emulated radio channel, not a live commercial network. The multi-user logs hold 189 files in 33 conditions: Trial 0 has twelve single-class conditions (eMBB, URLLC or mMTC with one to four users); Trials 1–3 are load sweeps with four to ten users. Preparation:
Read all 189 files; drop the single file without slicing columns.
Align each condition's users on common 250 ms intervals.
Compute cell-level quantities over all users before any filtering: cell load (sum of grants ÷ 12,500) and the number of users present.
Keep only records with slicing disabled: 601,592 of 735,117. With slicing on, a 14-PRB slice cap fixes the grant regardless of load, which is configuration, not congestion (Section 7.2).
Attach each user's traffic class from the trace lists (Trial 1 has none and is marked unknown).
Map columns onto the six shared measurements (Table 3).
6.4 Stage 1: defining congestion (the label)
The same code labels both sources. For each user and 250 ms interval:
Ratio = what the user gets ÷ what it needs (Table 4). Intervals with no demand have no ratio.
Starved (raw) when the ratio is below 0.5: the user receives less than half of what it needs.
Starved (state) with hysteresis: two starved intervals in a row to enter, two normal intervals in a row to leave. Single-interval blips are mostly noise. A gap in a user's record resets the state.
Onset at time t when the user is not starved at t and is starved at t + 1 s (four intervals). Where t + 1 s lies outside the record, onset is undefined.
Revision 2 placed the threshold at 0.415, the valley of a two-mode mixture. Section 7.2 shows that those two modes are slicing-on against slicing-off records, so on slicing-free data there is no valley to fit. The threshold is therefore set by meaning (less than half) and its effect is reported across 0.2–0.8 (Figure 13).
6.5 Stage 1: experiment datasets
Table 10. Experiments and the datasets built for them. Rows are user-intervals; onsets in brackets.
E2, E3 and E4 share one real test set, a fixed 30 % of each trial's conditions (Trial0 mmtc3, mmtc4, urllc1, urllc3; Trial1 multi4, multi10; Trial2 multi4, multi9; Trial3 multi6, multi10), so E4 − E2 compares models on identical data. E1 holds out the highest seed of every scenario. No user's record is split between training and testing, and the real slices in E3 are whole user sessions from outside the test set. Features are standardised with the training set's mean and deviation only. Automated checks confirm each of these properties.
6.6 Stage 2: models
Every model sees the last 2.5 s (ten intervals) of the six measurements for one user and outputs the probability of an onset one second later. Baselines set the floor: persistence (the label does not change), moving average, ARIMA, and gradient-boosted trees on windowed features, which often match small neural networks on tabular time series. The learned models are LSTM, TCN, GraphSAGE and a hybrid (Figure 4): a graph summary of all users in the same cell and interval is combined with the user's own history before a time encoder. The graph is not split by service class, because one class crowding out another is exactly what it should capture. All models are trained on the onset label directly and calibrated afterwards; no threshold is picked by hand.
Figure 4. Hybrid model (Stage 2). A graph summary of the other users in the cell supplies contention context to a per-user time encoder that outputs a calibrated onset probability.
The ablation replaces the graph summary with simple cell averages; if accuracy holds, message passing is not earning its cost, and that is reported. In the real data the graph has one to ten nodes per cell.

7. Stage 1 results
This section reports what the Stage 1 data shows, with every figure computed from the final datasets.
7.1 The simulator now produces congestion
Revision 2 reported that the old simulation barely congested: latency moved from 8.9 to 11.5 ms during the burst. After the repairs, starvation responds to load as a congestion label should (Figure 5 and Table 12).
Figure 5. Simulator scenarios. (a) Share of user-intervals starved, (b) onsets per 1,000 user-intervals, (c) handovers per user in 120 s. Bars are means over seeds, lines 95 % confidence intervals, dots individual runs.
Table 12. Simulator scenarios: means over seeds, ± half-width of the 95 % confidence interval. Peak cell load is the 95th percentile of a cell's PRB share.
Light load stays essentially uncongested (0.9 ± 1.7 %). The urban baseline starves 29.2 ± 4.3 % of intervals and heavy load 52.5 ± 1.1 %, a clean load gradient comparable to TRACTOR's response to user count (Section 7.2). Mobility changes handovers as intended (2.7 per user at vehicular speed against 1.4 at walking pace) but hardly changes starvation. Median latency rises from 5 ms to 275 ms, and the 95th percentile reaches seconds because a starved user's 128 KiB queue drains slowly.
Figure 6. (a) Downlink CQI before the repairs (grey, old run) and after (blue, urban runs): with the interference cells active, radio quality now spans the full range. (b) PRB share used per cell in the urban scenario: the macro cell runs near capacity while the micro cells are lightly used.
Two properties of the scenario matter for Stage 2. First, radio quality now varies (Figure 6a): the CQI spread between quartiles grew from 0.25 to 5.7, and its 5th percentile fell from 12.7 to 3.6. Second, load is concentrated (Figure 6b): on average 42 of the 50 users attach to the 46 dBm macro cell, whose median load is 87 %, while the micro cells sit at 8–22 %. Nearly all contention happens inside one cell, which resembles TRACTOR's single cell more than intended.
Figure 7. Downlink received ÷ sent per traffic group (box: quartiles; whiskers: 5th–95th percentile). In the urban scenario the video users are starved; in heavy load every group suffers.
Starvation falls on users whose demand is large relative to their link (Figure 7). In the urban scenario video users receive a median 0.33 of what is sent to them, while web and IoT users receive all of it. In heavy load the video median drops to 0.08 and web and IoT users, now at 0.64 Mbit/s, are starved in 40 % and 45 % of intervals. The scheduler shares PRBs fairly, so whoever needs the most PRBs per bit of demand is cut first.
Figure 8. The uplink burst (shaded) in an urban run. Users 0–29 offer 0.9 Mbit/s each and are served almost exactly that; the macro cell's uplink PRB use rises from about 11 % to 88 % without saturating.
The uplink never congests (Figure 8): during the burst users send 0.89 of the 0.90 Mbit/s they offer, and macro uplink use rises from 11 % to 88 %. Uplink starvation stays at 0–2 % in every scenario, so all labels are downlink, like TRACTOR's, and the Gradual scenario, which only reshapes the burst, behaves like the urban one. A heavier burst would be needed to study uplink congestion.
7.2 What the real data shows
Figure 9. Granted ÷ requested PRBs in TRACTOR, intervals with demand. (a) With slicing on, the 14-PRB cap pins 78 % of intervals between 0.2 and 0.4. (b) With slicing off there is one peak near 1.0 and a smooth tail; values above 2 are drawn at 2.
The two-mode shape is slicing, not congestion. With slicing on, 78 % of intervals sit between 0.2 and 0.4 (median 0.294) and 22 % at 1.0. With slicing off there is a single mode at 1.01 (58 % of intervals between 0.9 and 1.5) and a smooth tail, with no second mode (Figure 9). The 0.292 / 0.978 modes and the 0.415 valley in revision 2 therefore separated capped from uncapped users. The same holds for mMTC devices, described in revision 2 as permanently capped: their median is 0.29 with slicing on and 1.29 with slicing off, so no per-user baseline is needed.
Figure 10. TRACTOR, slicing off: starved share of active intervals (a) by the number of users present and (b) by traffic class. *Trial 1 has no trace list, so its users' class is unknown.
Starvation follows load (Figure 10a): 0.0 % of active intervals with one user, 0.1 % with two, 5.2 % with three, and 48 %–46 % with eight or nine. The curve is not monotonic because each user count comes from a few conditions with different traffic mixes; ten users rest on only 490 active intervals. By class (Figure 10b), URLLC users are starved most (13.8 %), eMBB 9.1 %, mMTC almost never (0.3 %).
Figure 11. Persistence and length of starvation. (a) Probability of still being starved a given time later; dashed lines are base rates. (b) Share of episodes at least a given length (log–log).
Starvation persists but episodes are short (Figure 11). A starved real user is still starved one second later 72 % of the time against a base rate of 2.2 %, which is why the target is onset, not state. Yet most episodes are brief: median 0.75 s, 90 % shorter than 2.5 s, longest 181 s. The simulator's episodes are somewhat longer (median 1 s, 90 % under 6.8 s). Results in Stage 2 are therefore reported per episode-length band.
Figure 12. Two minutes of one real eMBB user (Trial3/multi9). Shaded: starved state; triangles: onsets, i.e. intervals one second before starvation begins. Gaps in the line are intervals with no demand. Below: the cell's PRB load.
Figure 12 shows what the label looks like on a single user: starvation coincides with the cell's PRB load approaching 100 %, and each onset marks the moment, one second ahead, that a model must flag.
7.3 Choosing and checking the label
Figure 13. Sensitivity of the label to the threshold. (a) Starved share and (b) onsets per 1,000 user-intervals, both on a log scale. Solid vertical line: chosen 0.5; dashed: revision 2's 0.415.
Threshold. In TRACTOR the starved share rises steadily with the threshold, from 1.2 % at 0.3 to 2.2 % at 0.5 and 4.1 % at 0.7, with no plateau that would mark a natural cut (Figure 13). In the simulator the curve is nearly flat (29 % to 39 %): simulated starvation is deep, so most starved intervals are far below any reasonable threshold. 0.5 is kept for its plain meaning, and Stage 2 reports results at 0.3 and 0.7 as well.
Table 13. Checking ways to label the simulator against reference labels. Kappa: agreement beyond chance (1 = perfect, 0 = chance).
Simulator label. Revision 2 planned a proxy from cell load and a per-user throughput drop, validated on TRACTOR. Table 13 shows the result. A cell-saturation rule agrees well with the true label on TRACTOR (kappa 0.61) but not with the simulator's direct measurement (kappa -0.05; -0.13 at a 70 % threshold): in the multi-cell simulator the macro cell is near capacity much of the time, and which user starves depends on its own radio link, not on the cell. Rebuilding the simulator's byte ratio on TRACTOR also fails, for a different reason: when a real user is starved its downlink buffer is already standing (median 10 kB against 0), so served bytes plus buffer growth barely differ from served bytes. Real traffic adapts or is dropped, while the simulator's constant-rate traffic does not. The simulator is therefore labelled with received ÷ sent bytes, which is exact there (Section 4.4); the remaining difference between the two labels is stated as a limitation.
7.4 Simulation against reality, before any model
Figure 14. Distribution of each shared input in the simulator (all intervals) and in TRACTOR (intervals with demand), as cumulative shares. The Kolmogorov–Smirnov distance is the largest vertical gap (0 = identical, 1 = no overlap).
Table 14. The shared inputs in both sources: medians and distance.
Only uplink SINR is well aligned (Figure 14, Table 14). Cell load and CQI differ in opposite ways: the simulated macro cell is busier but its radio is better. Real users move far more data when active, and the simulated uplink error rate (median 24 %) has no counterpart in the real data, where half of active intervals have no errors at all. Label prevalence differs by an order of magnitude (Figure 15a): 34.1 % of simulated intervals are starved against 2.2 % of real ones, and onsets are 6.6 % against 0.6 %.
These gaps exist before any model is trained, and they shape Stage 2:
A model trained on the simulator will see real inputs outside its training range; E2 measures the cost.
Probabilities calibrated on simulated data will be far too high on real data; calibration is evaluated per source and precision–recall AUC is the primary metric.
Standardising each source with its own statistics, and dropping the uplink error rate, are tested as ablations.
The uplink-SINR alignment and the shared load–starvation relationship (Figures 5 and 10) are what a model can hope to transfer.
7.5 Datasets ready for Stage 2
Figure 15. (a) Share of intervals starved and with an onset in each source. (b) Train (grey) and test (coral) rows per experiment; labels give onsets in train / test.
All seven datasets (Figure 15b) pass the automated checks: no user record crosses train and test, E2–E4 share one test set, E3's real rows come only from the training pool, and features are standardised with training statistics. E5 has only 237 onsets to learn from, since four to six users rarely starve, against 1,355 to predict at nine or ten users; that imbalance is the point of the experiment.
8. Deployment context
The model is designed as an xApp on the near-RT RIC (Figure 2): it would read the six measurements for each user over E2 every 250 ms, keep a 2.5 s history and output an onset probability within the same interval. Training and lifecycle management sit in the Non-RT RIC and SMO; A1 carries policy down and no telemetry. Because every input is an E2SM-KPM quantity [21], the model needs no node-internal state and no handset instrumentation. Deployment and closed-loop evaluation are not performed here; the intended next step is a simulated control loop inside OMNeT++ in which predictions bias the scheduler and the change in quality of service is measured, described as a simulated loop rather than an xApp.
9. Limitations
One real cell. TRACTOR is single-cell, so the graph models contention among users of one scheduler, not spatial structure across cells.
Emulated radio. TRACTOR's channel is emulated, not over the air.
MAC-level inputs. The transferable inputs are almost all MAC-layer quantities, which recent work finds insufficient on their own to describe user experience [6].
Different label instruments. The real label is PRB-based, the simulated one byte-based. They agree in principle (Section 4.4) but cannot be checked against each other directly; an identical label needs Simu5G patched to emit requested PRBs.
Different traffic. Simulated traffic is constant-rate; real traffic is bursty and adapts to the network. Real users have demand in 22 % of intervals, simulated users in all of them.
Large shift before modelling. Four of six inputs differ strongly (KS 0.39–0.76).
Real trials are not repeats. Trials 2 and 3 assign the same trace to the same user in 2 of 49 cases, and Trial 1 has no trace list.
Few seeds. Three to five seeds per scenario leave wide confidence intervals for some quantities.
No uplink congestion in the simulator.

11. Stage 2 plan and future work
11.1 Stage 2 steps
Run the floor baselines (persistence, moving average, ARIMA, gradient-boosted trees) on E1–E5.
Train LSTM, TCN and GraphSAGE under one protocol with several seeds and confidence intervals.
Build the hybrid model and its ablation against simple cell averages.
Calibrate every model; report precision–recall AUC, reliability, warning time, false alarms on calm conditions, results per episode length, parameter count and inference time.
Test per-source standardisation and the removal of the uplink error rate as ablations.
Report the transfer gap (E4 − E2), the real data needed to close it (E3) and load extrapolation (E5).
11.2 Optional strengthening
More seeds for the scenarios with wide confidence intervals (up to ten are configured).
A heavier uplink burst, so that uplink congestion can be studied.
A topology matched to TRACTOR (one cell, four to ten users) to separate topology mismatch from the sim-to-real gap proper.
11.3 Future applications
Closing the loop, so that a predicted onset triggers a scheduling or mobility action rather than an alarm.
Energy saving, by predicting intervals in which a cell can be powered down without harm.
Protecting latency-sensitive traffic from broadband contention before degradation occurs.
Intent-driven operation, where the network's own predictions determine the configuration needed for an operator's goal.
